## B. Framework comparison

| Option | Reach and UI | Native integration | Tooling / risks | Assessment |
|---|---|---|---|---|
| Flutter + Dart | Official stable Android, iOS, Windows, macOS, Linux and web targets; one UI/domain codebase; highly controllable visual system | Plugins plus platform channels/FFI; use native Kotlin/Swift for widgets and integrations | Flutter SDK missing here; its custom-rendered UI requires deliberate platform adaptation; per-plugin target coverage varies | **Recommend**: broad currently stable reach and excellent custom UI control for the stated product |
| Kotlin Multiplatform + Compose Multiplatform | Shared Kotlin UI on Android/iOS/desktop; current official docs call WebAssembly web Beta | Strongest path to Android APIs/Glance; iOS uses Kotlin/Native and Swift/Objective-C interop; widget extension still native | More evolving web support; Windows build can work here; iOS builds still need Mac/Xcode; plugin/library compatibility requires version alignment | Strong alternative if Android/native-widget priority outweighs web certainty; not selected because web is a named future platform |
| React Native + Expo + TypeScript | First-class Expo Android, iOS, and web; native components on mobile | Expo supports custom Kotlin/Swift modules and config plugins; widget integrations need native targets | desktop beyond Expo is a community route; some Expo cloud services are optional paid tiers (not needed for basic local development); widget parity is not automatic | Viable, especially for an existing TypeScript team; less consistent across requested desktop/widget targets |
| Fully native Android and iOS | Best control of OS UI and system behavior | Direct APIs; Android Kotlin and Apple Swift/WidgetKit/EventKit | Separate UI and likely separate domain implementations for desktop/web; highest duplicated work and maintenance burden | Excellent platform-specific experience but a poor fit for one person and the full target matrix |
| Native apps with shared KMP domain | Native platform UI, shared scheduling rules | Direct native integration in Android/Swift wrappers | Still requires multiple UIs and build/test environments | Best if native polish becomes more important than reuse, but not the initial direction |

Flutter is open source under BSD-3-Clause; Compose Multiplatform is open source from JetBrains and stable for mobile/desktop but its WebAssembly target is Beta; Expo itself is free/open source, while its optional cloud services are separate. Flutter’s official current support matrix lists Android API 24+, iOS 15+, Windows 10+, macOS 12+ (Intel support is being deprecated), Debian 10+, Ubuntu 20.04+, and modern browsers. These are framework support floors, not a final product minimum-version decision. See the [Flutter platform matrix](https://docs.flutter.dev/reference/supported-platforms), [Flutter FAQ](https://docs.flutter.dev/resources/faq), [Compose Multiplatform compatibility](https://kotlinlang.org/docs/multiplatform/compose-compatibility-and-versioning.html), [Compose platform status](https://kotlinlang.org/compose-multiplatform/), and [Expo FAQ](https://docs.expo.dev/faq/).

**Limitations to carry forward:** Flutter renders most application UI itself rather than hosting each OS's default native widgets. “Native quality” therefore means platform-appropriate navigation, touch/keyboard/focus semantics, accessibility, system integrations, and visual adaptation; it does not mean identical native controls. iOS builds, signing, WidgetKit work, and physical-device acceptance need a Mac/Xcode path. Web/desktop may need responsive layouts and input models distinct from phones.

## D. Platform facts that affect scope

- Android widgets are `AppWidget` surfaces; Glance is Kotlin and emits constrained remote views. Periodic widget update minimum is 30 minutes; user/system triggers can refresh earlier, but Doze, WorkManager quotas, process death and OEM policy can delay work. Never promise a ticking countdown that updates every minute. Store next events in a compact widget snapshot; refresh on app changes, date/time/time-zone changes and allowed scheduled callbacks. See [Android widget updates](https://developer.android.com/develop/ui/views/appwidgets/advanced) and [Glance](https://developer.android.com/develop/ui/compose/glance).
- WidgetKit uses a proposed timeline and refresh policy; iOS decides when to reload and can delay a requested date. Widget content must remain useful when stale and include an explicit last-updated state where that helps. See [WidgetKit timelines](https://developer.apple.com/documentation/widgetkit/timeline?changes=_8).
- Android Calendar Provider supports querying/writing calendars with runtime permission; Android docs recommend system intents for simple create/view flows. Apple EventKit supports write-only or full access on current OS versions; EventKitUI can present a user-mediated event editor without broad read access in appropriate flows. Start with explicit export/“add event” consent, rather than continuously mirroring calendars. See [Android Calendar Provider](https://developer.android.com/identity/providers/calendar-provider) and [Apple EventKit](https://developer.apple.com/documentation/eventkit/accessing-calendar-using-eventkit-and-eventkitui?changes=_7).
- Android 13+ notification permission and Android 12+/14+ exact-alarm restrictions require graceful degradation. Exact alarm access is not universally granted; use only for user-configured, genuinely precise reminders, explain the value, check permission, and provide best-effort alternatives. OEM battery management may further delay notifications. See [Android exact alarm behavior](https://developer.android.com/about/versions/14/changes/schedule-exact-alarms).
- Android Auto Backup may copy app-private files to a Google account depending on app/platform settings; the default must be reviewed explicitly against the “no cloud required” privacy promise. Offer a local export/restore route, and decide whether Android device transfer is opt-in or disabled by default. See [Android Auto Backup](https://developer.android.com/identity/data/autobackup).
- Android update installation requires same signing identity and package ID; for self-distribution, losing the private signing key prevents in-place updates without changing the app identity and migrating data. Build APK for direct install; AAB is a store upload format, not the artifact intended for direct install. Keep monotonic version codes and tested database migrations. See [Android app signing](https://developer.android.com/studio/publish/app-signing).

## E. Private APK policy snapshot

As of 2026-11-05, Google says the September 30, 2026 first-phase developer-verification deadline applies to participating stores in selected rollout contexts; its FAQ says direct sideloading and other non-participating stores are not affected by that first phase and recommends developers plan before a wider 2027 rollout. That means private APK distribution is still a viable current route, but the rule is in transition and country/device scope can change. Before sharing outside the owner's own devices, check the current [Android developer verification FAQ](https://developer.android.com/developer-verification/guides/faq) and package-registration guidance. Do not assume “sideloaded” means permanently exempt.

Use a release-signed APK for distribution, not debug builds. Generate and protect one app-specific signing key with at least two secure backups, record the alias/package ID/versioning process without storing secrets in Git, verify checksums/signature before transfer, and document installation/update steps. Never put signing material in the repository or cloud issue/chat. APKs do not install natively on iPhone/iPad; Apple distribution requires an iOS build and a separate Apple signing/provisioning path.
